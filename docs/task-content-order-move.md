# Задача: order — автоназначение при создании + move-эндпоинты (категории и уроки)

## Контекст

Строим master-раздел Content. Перестановка порядка в интерфейсе будет
кнопками вверх/вниз. Аудит (task-content-api-audit) показал:

- `order` сейчас приходит из тела запроса с default 0 → все записи
  получают 0, сортировка де-факто по id;
- логики сдвига/обмена order нет нигде;
- `order` не уникален (ни в моделях, ни в миграциях) — дубли возможны.

Контента в базе dev пока нет (categories/lessons = 0), миграция данных
не требуется. Но защиту от дублей order закладываем в сервис (см. ниже).

## Что сделать

### Часть 1. Автоназначение order при создании

**Категории** (`category_service.create_category` или аналог):

- Убрать `order` из `CategoryCreateIn` (клиент его больше не передаёт).
- При создании сервис сам назначает `order = max(order) + 1` среди
  категорий **с тем же `parent_id`** (включая `parent_id IS NULL` для
  верхнего уровня). Если соседей нет — `order = 1`.

**Уроки** (`lesson_service.create_lesson` или аналог):

- Убрать `order` из `LessonCreateIn`.
- При создании `order = max(order) + 1` среди уроков **той же
  `category_id`**. Если уроков в категории нет — `order = 1`.

**PATCH:** поле `order` из `CategoryUpdateIn` и `LessonUpdateIn` тоже
убрать — порядок теперь меняется только через move-эндпоинты, чтобы
не было второго пути с ручными значениями и дублями.

⚠️ Если урок через PATCH переносится в другую категорию
(`category_id` меняется) — сервис назначает ему `order = max + 1`
в новой категории (встаёт в конец). Аналогично для категории при
смене `parent_id`, если PATCH это уже умеет (если не умеет — не
добавлять, это отдельная задача).

### Часть 2. Move-эндпоинты

Два новых эндпоинта, оба **только master** (существующий
`Depends(require_master)`), теги Swagger как у соседних роутов:

```
POST /api/category/move/   тело: {"id": int, "direction": "up" | "down"}
POST /api/lesson/move/     тело: {"id": int, "direction": "up" | "down"}
```

Схемы запроса: Pydantic с `Literal["up", "down"]` для direction
(кривое значение → стандартный 422).

**Логика (общая для обоих, в services/):**

1. Найти запись по id. Нет → 404 `"Category not found"` /
   `"Lesson not found"` (тексты как в существующих сервисах).
2. Определить «ряд соседей»: для категории — записи с тем же
   `parent_id`; для урока — записи с той же `category_id`.
   Сортировка ряда: `order, id` (как в текущей выдаче).
3. **Нормализация при дублях:** если в ряду есть повторяющиеся
   значения `order`, перед перемещением пронумеровать ВЕСЬ ряд
   заново (1, 2, 3, … по текущей сортировке `order, id`).
   Это страховка на случай старых данных с order=0.
4. Найти соседа: для `up` — предыдущий в ряду, для `down` — следующий.
   Соседа нет (запись уже первая/последняя) → **200** с телом
   `{"status": "noop", "id": <id>}` — это не ошибка, интерфейс просто
   ничего не перерисует. Кнопки в UI будут задизейблены на краях,
   но защита нужна и на бэке.
5. Обменять значения `order` записи и соседа. Один `db.commit()`
   на всю операцию (нормализация + обмен в одной транзакции).
6. Успех → 200 `{"status": "moved", "id": <id>}`.

**Переиспользование:** логика move для категорий и уроков почти
одинакова — вынести общую часть в приватную функцию-помощник, если
это получается чисто (разные модели и разные поля «родителя»).
Если обобщение выходит запутанным — лучше две простые явные функции,
чем одна хитрая. Решение оставляю за тобой, но без копипасты
нормализации.

### Часть 3. Роуты и подключение

- Роуты положить в существующие файлы `api/v1/categories.py` и
  `api/v1/lessons.py` рядом с остальными эндпоинтами этих сущностей
  (не создавать новые файлы).
- Порядок путей: `/api/category/move/` — это отдельный путь, конфликтов
  с `/api/category/` быть не должно, но проверь, что FastAPI матчит верно.

## Чего НЕ делать

- НЕ добавлять уникальные ограничения/индексы на `order` в БД —
  консистентность держит сервис, миграций в этой задаче быть не должно
  (поля не меняются, только логика).
- НЕ трогать `GET`-эндпоинты, схемы ответов (`CategoryOut`,
  `LessonCardOut`, `LessonOut`) и правило видимости.
- НЕ добавлять `parent_id` в PATCH категории — это следующая задача.
- НЕ делать drag&drop-заготовок, bulk-перестановок, эндпоинта
  «задать порядок списком».

## Testing guide (напиши свой по этому скелету)

Через Swagger под сессией keimo:

1. Создать категорию A → в `GET /api/categories/` у неё `order = 1`.
2. Создать категории B и C → order 2 и 3, выдача в порядке A, B, C.
3. `POST /api/category/move/` `{id: C, direction: "up"}` → порядок A, C, B.
4. Двинуть A вверх → ответ `{"status": "noop"}`, порядок не изменился.
5. Создать 2–3 урока в одной категории, проверить order 1, 2, 3
   и перемещение вниз/вверх аналогично.
6. Проверить 404 на несуществующий id и 422 на `direction: "sideways"`.
7. Убедиться, что POST категории/урока с полем `order` в теле теперь
   его игнорирует или отвергает (описать фактическое поведение).
